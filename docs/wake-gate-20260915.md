# 2026-09-15 唤醒词英文识别与唤醒监听流量修复

本轮首次接通板端串口（`COM15` / 1500000 8N1 / CH343），因此下面所有结论都有
**逐字串口日志**支撑，不是从源码推断。原始日志留在
`_work/wake-debug-20260915/serial-*.log`（VM 与 Windows 各一份）。

## 一、起因

用户真机反馈：

1. 「唤醒词是英文的检测不到呀」——英文唤醒词喊不醒。
2. 「开启唤醒词他就一直识别语音转文字什么的，没有其他更好的方案吗？」
3. 「为什么他经常不能说话」。

三条反馈指向同一个模块，但根因是三个**互相独立**的缺陷。

## 二、真机诊断

### 2.1 短语匹配本身是对的，错的是命令

在 `vela>` 提示符下逐条执行（`voice_wake_test` 不依赖麦克风、网络或 Key）：

| 用例 | 期望 | 2026-09-15 实测 |
|---|---|---|
| `voice_wake_test Hello，openvela` | yes | **yes** |
| `voice_wake_test Hello, openvela` | yes | **no** ← 缺陷 A |
| `voice_wake_test hello openvela` | yes | **no** ← 缺陷 A |
| `voice_wake_test 你好，openvela` | yes | **yes** |
| `voice_wake_test Hello，OpenVela` | yes | **yes** |
| `voice_wake_test 你好小米` | no | **no** |

**结论**：`voice_wake_matches()` 对英文完全正确，2026-09-13 的记录是准确的。
真正的问题是 `cmd_voice_wake_test()` **只取 `argv[1]`**：NSH 按空格分词，
`Hello, openvela` 被截成 `Hello,`，规范化后只剩 `hello`，于是打印 `no`。
用英文键盘输入这句时几乎必然踩到，而报告正是引用这条命令当证据。

### 2.2 语音识别把英文按中文解码（缺陷 B）

`src/voice/mimo_asr.c` 把请求写死成：

```c
cJSON_AddStringToObject(options, "language", "zh");
```

小米官方文档（语音识别 / MiMo-V2.5-ASR）写明：

> 使用 `asr_options.language` 指定语种，**未配置时为自动检测**。
> 支持取值：`auto`、`zh`、`en`。

且该模型「支持中英双语识别及**自动语种检测**……自动识别语码混用中的各语言内容」。
写死 `zh` 之后，对着麦克风说 `Hello，openvela` 会被强行按中文解码，
转写文本里不会出现 `helloopenvela`，匹配必然失败。
这解释了「中文喊得醒、英文喊不醒」的全部现象。

### 2.3 唤醒监听空转（缺陷 C，也是"经常不能说话"的根因）

`voice_wake_start` 后静置 65 秒，串口日志统计：

| 指标 | 实测 |
|---|---|
| 云端 ASR 上传 | **20 次**（上传时间戳平均间隔约 **4.3 秒**） |
| 每次上传体积 | **80,000 字节** PCM |
| TLS 握手 | **21 次**（每次上传一次完整握手，无连接复用） |
| 静音时的识别结果 | `诶。` / `1.` / `1.` / `<chinese> Yeah.` / `邪恶猫猫，你觉得男生是？` / `你来，你来，你好。` … |

房间是安静的，设备却每 4.3 秒上传 80 KB 音频并做一次完整 TLS 握手，
**7×24 不停**，换回来全是幻觉文本。折合约 **840 次/小时、约 2 万次/天**。

后果：持续消耗 ASR 额度与流量；抢占 WiFi / TLS / CPU，前台问答与 TTS 播报被拖慢
——这就是「经常不能说话」的直接原因。

## 三、顺带确认的两件事

### 3.1 TTS 播报真机是能出声的

```
[voice] TTS network done: 3318ms
[audio_pb] nxplayer fallback playback: 1760ms
nxplayer> playraw /data/ai_agent/tts_stream.pcm 1 16 24000 0
sunxi_audio_start index:0
play_workerthread:set param format:2 rate:24000 ch:1 period_size:1024 buffer_size:4096
[audio_pb] nxplayer fallback finished: status=0 bytes=84480
[voice] speak done: total 5353ms (play wait 2035ms)
MiMo TTS playback OK.
```

`media_player_open()` 在这块板子上返回 NULL（媒体服务 RPC 路径不可用），
但 `audio_playback.c` 的 **nxplayer 回退路径可用**：PCM 落到
`/data/ai_agent/tts_stream.pcm`，再由 NxPlayer `playraw` 播放，84480 字节播放成功。
**设备能说话**；日志里的 `media_player_open failed` 是误导性告警，不是故障。

用户此前日志中的 `TTS stream failed: -71`（`EPROTO`）出现在 TTS **网络流**上，
不是播放。本轮在唤醒监听同时运行的条件下重测 `voice_test_speak`，
依然 `MiMo TTS playback OK.`（total 4526ms）——该 `-71` 是瞬时网络错误。

### 3.2 采集侧一直是好的

`audio_capture.c` 有 `CONFIG_AI_AGENT_AUDIO_ALSA_DIRECT` 直通 ALSA 路径
（`hw:snddmic`），所以 ASR 一直拿得到音频
（`batch ASR result: 豆包的免费额度怎么用呢` 就是现场成功证据）。

## 六、"有没有更好的方案"——诚实的回答

现在的唤醒是**云端批量 ASR 轮询**：录音 2.6 秒 → 整段上传 → 云端转写 → 本地匹配。
它不是离线唤醒，也不是流式唤醒。本轮的门控把它从"永远在上传"压到"只在有人说话时上传"，
但没有改变它的本质。按代价从低到高：

1. **已做（本轮）**：本地端点门控。零网络请求地过滤静音，消掉全部空转上传。
2. **下一步可做**：命中缓存 + 复用 TLS 连接。当前每轮都重新握手；
   代码里 `voice_asr_stream_open()` 在流式后端不可用时每轮都失败重试两次，
   可缓存"不支持流式"的结论。
3. **真正的解法**：本地关键词唤醒（KWS）——麦克风数据不出板，
   唤醒延迟从秒级降到百毫秒级，且不依赖 Key 和网络。
   但 R528S3 上需要移植/训练一个小模型，**按剩余时间（截止 9-20）不现实**，
   不写入承诺。

## 八、本轮踩到并修好的构建阻塞（重要教训）

构建第一次跑到最后一步失败：

```
packages/demos/Kconfig:19: 'packages/demos/minui/Kconfig' not found
make: *** [tools/Unix.mk:749: savedefconfig] Error 1
Error: ############# save .../configs/nsh/ fail ##############
```

**注意失败位置**：LTO 链接、`nuttx.bin`、ELF 都已经生成，只在最后的
`savedefconfig` 读取 Kconfig 时才炸——所以现象很像"代码编译失败"，实际不是。

### 根因链

1. `packages/demos/minui` 是一个**指向专属仓的符号链接**：
   `packages/demos/minui -> ../../contest2026_120_haohaoxuexitiantianxiangshang/app/minui`
2. `packages/demos/Kconfig` 是 **gitignored 的自动生成文件**
   （`.gitignore:5:/Kconfig`，由 `apps/tools/mkkconfig.sh` 生成），
   它按 `ls -1 */Kconfig` 把 `minui` 写了进去。
3. 2026-09-15 的仓库卫生轮删掉了 `app/minui/` 里**被追踪**的文件——其中包含
   `app/minui/Kconfig`。`git rm` 只删被追踪的文件，**目录本身和未追踪产物会留下**，
   所以 `app/minui/` 还在（里面是 `*.o`、`*.bak-*`、`.built`、`Make.dep`），
   但**没有 `Kconfig` 了**。
4. 于是那条 `source` 指向一个没有 `Kconfig` 的目录 → `savedefconfig` 失败。

**关键点**：符号链接本身没断（目录还在），断的是目录里的 `Kconfig`。
所以 `find -xtype l`（查悬空链接）**查不出来**——这个坑用常规手段发现不了。

### 修法（纯 VM 本地，不进任何仓库）

```bash
rm /home/openvela/openvela/packages/demos/minui          # 未追踪的符号链接
cd /home/openvela/openvela/packages/demos
bash ../../apps/tools/mkkconfig.sh -m Demos              # 重新生成 Kconfig
```

并顺手把两个目录里的**未追踪残留**移出工作区（不是删除，移到
`_work/wake-gate-20260915/removed-leftovers/`，共 13 个文件 1.5 MB）：
`app/minui/`（1.3 MB，含两个 466 KB 的 `.o`）、`app/study_terminal/`（160 KB，2 个 `.bak`）。
两者 `git ls-files` 计数均为 **0**，确认全部未追踪。

### 为什么这不影响提交

- `packages/demos/minui`：**未追踪** → 不属于任何仓库；
- `packages/demos/Kconfig`：**被 gitignore** → 自动生成，不属于任何仓库；
- `app/minui`、`app/study_terminal` 的残留：**未追踪**。

因此 **PR #3（删除 `app/minui/`）不会破坏上游构建**——上游既没有这个符号链接，
也没有那份生成出来的 Kconfig。它只破坏了**本 VM 的本地构建环境**。

反过来看也更安全了：现在符号链接没了，任何人重新生成 `packages/demos/Kconfig`
都会得到一份**不含 minui** 的正确文件。

### 复用价值

> **删除某个目录里被追踪的 `Kconfig` 时，必须先检查有没有 `packages/*` 下的符号链接
> 指过来，并同步重新生成父级自动 Kconfig。** `git rm` 不会删掉目录，
> 而父级 Kconfig 是 gitignored 的，所以两边都不会在 `git status` 里报警——
> 只有构建到 `savedefconfig` 那一步才会暴露，且报错位置具有误导性。

## 九、候选链的重新推导（让"这份镜像确实由受审源码构建"可证）

打包前发现一个必须处理的问题：本轮源码是**直接拷进树里的**，`source/` 落在后面，
而 `SOURCE_MANIFEST.json`（继承基线）还是打补丁之前的内容。两个后果都会把验证变成走过场：

1. `audit_candidate.py` 把本轮补丁报成 `unexpected`（"不是归档来源的漂移"）。
   按流水线约定，这等于"有人手改了树"，不解释清楚就不能继续；
2. `candidate-manifest.json` 还是**更早那一版补丁**生成的，`cmd_voice.c` 与
   `voice_wake.c` 的 `after_sha256` 与树不符 → `verify_pair.py` 的哈希断言必然失败。

**没有手改任何清单**——那会把"可证"降级成"声明"。改的是流程，让它重新推导一遍：

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | 记录 10 个漂移文件在当前树里的最终内容（`rederive-snapshot.json`） | 10 项哈希 |
| 2 | 用树的最终内容补齐 `source/`（候选 = 最终内容） | 刷新 7 个 |
| 3 | 把树回退到记录的基线（`baseline/` 逐字节校验后才覆盖） | 10 个全部回到基线 |
| 4 | `rebaseline_candidate.py` | `rebased_files: 0`（确认树 == 基线） |
| 5 | `audit_candidate.py` | `changed_files: 10`、**`unexpected_changes: 0`** |
| 6 | `sync_candidate.py` | 应用 10 个，失效 124 个目标 → 强制全量重编 |
| 7 | 复核树 == 第 1 步快照 | **10/10 一致** |
| 8 | `build_candidate.sh` → `verify_pair.py` | 见 §五 |

**第 7 步是这套做法的关键**：它证明"重新推导"没有把树改成别的东西——重新同步后的树
与重建前逐字节相同，所以本轮的镜像仍然出自同一份源码，只是现在**可证**了。

### 白名单的一次合理放宽

`sync_candidate.py` 的 `allowed` 原本只允许 `packages/ai_agent/` 与
`contest2026_.../app/hello_app/`。本轮触发了第三个：

`vendor/allwinnertech/boards/r528/r528s3-dshanpi/configs/nsh/defconfig`

原因不是手改，而是**构建归一化**：基线 defconfig 里还留着 `CONFIG_LVX_USE_DEMO_MINUI=y`，
但 2026-09-15 的卫生提交删掉了 `app/minui`，该符号的 Kconfig 已不存在，
`savedefconfig` 会把它丢掉。归一化后的 defconfig（少一行）是稳定不动点，
**必须作为候选的一部分**，否则 `verify_pair.py` 对基线里 defconfig 的哈希断言永远对不上。

### 教训（可复用）

- **别绕过 `source/` 直接往树里拷源码。** 一旦绕过，`source/`、基线、清单三者开始
  各自漂移，而且是**静默**的——直到 `verify_pair.py` 报一个看不懂的哈希错才暴露。
- **`build.log` 每次构建都被覆盖。** 增量构建只编改动过的单元，所以单份日志凑不齐
  `CC:` 断言。要么一次性 `touch` 全部需要的单元再构建，要么像本轮这样让
  `sync_candidate.py` 失效目标、强制全量重编。
- **`pgrep -f` 会匹配到自己那条命令**（假 RUNNING）。改用
  `ps -eo pid,etime,cmd | grep -v grep`，或轮询 `build.exit` 这类落地文件，
  并**确认它的 mtime 属于本轮**（旧轮次的完成标记会骗人）。
