## 二、然后发现：端点门控**根本没生效**

`voice_wake_start` 之后静置 65 秒，一个字都不说。实测：

| 观察点 | 修复前（09-15 用户日志） | 本轮实测 | 期望 |
|---|---|---|---|
| `batch ASR (with_text)` | 约 14 次/60 s | **16 次 / 69 s** | **0 次** |
| `vela_tls Handshake OK` | 约 14 次 | **16 次** | **0 次** |
| `endpoint gate: silence` | — | **0 次** | 每轮一次 |
| `endpoint gate: speech` | — | **1 次** | 仅说话时 |

即：**门控代码在镜像里（否则不会打出 `endpoint gate`），但每一轮都判成"有语音"放行。**
周期约 4.3 秒：录 2500 ms（25 chunk × 3200 B）→ 上传 80,000 B → 握手 → 识别 → 再来一轮。

### 铁证是这一行

```
[voice] recording thread exit: 25 chunks, 80000 read, 0 sent
[voice] endpoint gate: speech 0ms, uploading
[voice] batch ASR (with_text): 80000 bytes
[voice] batch ASR result: 你觉得他们大不大？
```

**`speech 0ms`** —— 门控读到的 `voiced_ms` 是 **0**，却走了"有语音"分支。
两个读数在同一个互斥锁里取，所以不是竞态，是**逻辑**：

```c
if (sum / count >= 250 && peak >= 1200) {
    s_voice.voiced_ms += duration;          /* 连续有声才累加 */
    if (s_voice.voiced_ms >= 200) s_voice.speech_seen = true;
} else {
    s_voice.voiced_ms = 0;                  /* ← 一旦安静就归零 */
    s_voice.quiet_ms += duration;
}
```

`voiced_ms` 会在第一个安静 chunk 上归零，而 **`speech_seen` 一旦置位就在整个窗口里黏住**，
直到下一轮录音开始才清零。而 09-15 的门控判的正是 `speech_seen`：

```c
if (!speech_seen) { /* 静音，跳过上传 */ }   /* ← 09-15 的写法 */
```

### 为什么每轮都能把 `speech_seen` 拉起来

采集通路的**起始瞬态**。实测每轮头几个 chunk 的峰值：

```
chunk#1: peak=11778 ~ 32768     ← 巨大
chunk#2: peak=1248  ~ 15858
chunk#3: peak=774   ~ 5592
```

`track_utterance()` 里有 `captured_ms > 200` 的跳过窗，但瞬态**比这更长**：
chunk#3 起开始被评估，峰值经常 ≥ 1200，连着两个 chunk 就把 `voiced_ms` 推到 200，
`speech_seen` 置位 → 门控永久打开。

**这就是用户说的「开启唤醒词他就一直识别语音转文字」的确切机理。**
识别结果也印证了是空音频幻觉：`你觉得他们大不大？` `说话也好打发。` `八嘛。`
`Oh.` `Why?` `Yeah.` `Okay.` —— 全是静音上的经典幻觉，而且**没有一条**匹配唤醒词
（`wake phrase matched` = 0 次），所以也从来没误唤醒。

## 三、排除掉的两个假设（都做了实验）

`token-plan-cn.xiaomimimo.com` 的配额或连接预算耗光了。做了一个 4 分钟压测：

```
22:31:36  开始 240 秒静音压测
```

结果：**压测期间 64 次 ASR 上传、65 次 TLS 握手，压测后 TTS 依然成功**
（`MiMo TTS playback OK` = 1 次，`TTS stream failed` = **0** 次）。
另外单独重复播报 8 次：

| 次数 | 结果 | 耗时 |
|---|---|---|
| 1–8 | **8/8 成功** | 3971 / 4162 / 4318 / 4435 / 4564 / 4572 / 4761 / 5615 ms |

**结论：TTS 链路本身是好的，ASR 空转没有把它饿死。** 用户看到「不能说话」的真正原因，

既没匹配到唤醒词，也就不会进入回答与播报。

## 五、本轮修复

### 5.1 判据换成**绝对累计有声时间**

`voice_channel.c`：

```c
/* 窗口内累计有声时长，安静 chunk 不会清零它。 */
uint32_t voiced_total_ms;
```

```c
    if (sum / count >= 250 && peak >= 1200) {
        s_voice.voiced_ms += duration;
        s_voice.voiced_total_ms += duration;   /* ← 新增，不归零 */
```

门控只判一个条件：

```c
    bool speech = voiced >= s_gate_min_voiced_ms;
```

- `voiced_total_ms` 在窗口内**只增不减**，所以说话末尾的静音不会把它抹掉；
- 一句话（约 1 s / 2.5 s 窗口）远超 500 ms，能过；
  起始瞬态（100–300 ms）远不到 500 ms，过不去。

默认值来自本轮实测：`min_voiced_ms = 500`。

> **为什么不用占空比**：第一版还加了"有声占比 ≥ 25%"这个条件，
> 主机测试立刻把它打回来了——占空比**依赖窗口长度**。
> 测试夹具的 PCM 缓冲是 10000 ms，板端是 2500 ms，
> 同一段 700 ms 的语音在两边算出 **7% vs 28%**，
> 于是真话被当成噪声丢掉，`wait_count` 断言超时。
> 绝对毫秒数与配置无关，所以最终只保留绝对阈值。
> （调试痕迹：`GATE dbg: voiced=700 captured=10000 duty=7 speech=0`。）

### 5.2 阈值做成运行时可调，不再靠猜

新增 `voice_gate` 命令：

```
vela> voice_gate                    # 看当前阈值
Endpoint gate: min_voiced_ms=500
vela> voice_gate 800                # 改阈值，立即生效，不用重烧
```

配套 `voice_channel_gate_get/set()`（`voice_channel.h` 声明）。
**这样下一轮可以在真机上量出噪声底，再对着数字调，而不是拍脑袋定阈值。**

### 5.3 日志带上数字

```
[voice] endpoint gate: silence voiced=200ms of 2500ms, ASR upload skipped
[voice] endpoint gate: speech voiced=1200ms of 2500ms, uploading
```

这两行就是调阈值需要的全部信息。仍然沿用"状态跳变才打印"的写法，长时间静音只出一行。

### 5.4 主机测试加了回归用例

`tests/voice_integration.c` 新增 `pcm_pattern == 3`：窗口头部 4 帧有声，
**够把 `speech_seen` 拉起来，但累计有声时间远不到 500 ms**，
断言 `voice_channel_stop_with_text(..., true) == -EAGAIN`。

A/B 对照：把**补丁前**的门控放回去，voice 套件就在
`voice_integration.c:464`（正是这个新用例）失败。
**说明这个用例复现的确实是板端缺陷，而修复就是让它通过的那一处改动。**
